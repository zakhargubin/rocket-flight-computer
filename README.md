# Rocket Flight Computer 

## 1. Что это за проект

Это минимальный учебный прототип бортового компьютера ракеты на C++17.

Проект не пытается быть прошивкой для реального полёта. Его задача — показать:
- объектно-ориентированную архитектуру;
- опрос датчиков через общий интерфейс;
- логирование телеметрии;
- простой автомат фаз полёта;
- подготовку к дальнейшему переносу на реальное железо.

Сейчас проект работает с **генератором сценария полёта**. Он подменяет реальные датчики и выдаёт данные так, как будто датчики уже подключены.

## 3. Cтандарт C++

Для этого проекта выбран **C++17**.

### Что из C++17 нам полезно
- `std::array`;
- `std::unique_ptr`;
- `enum class`;
- uniform initialization;
- аккуратная работа с `std::string`;
- нормальная поддержка современного CMake.

### Что мы сознательно не делаем
Даже при использовании C++17 проект пишется в ограниченном стиле:
- без исключений в основной логике;
- без рекурсии;
- без динамического выделения памяти в рабочем цикле;
- без тяжёлой шаблонной магии;
- без сложной иерархии наследования.

Идея простая: **использовать удобства C++17, но писать код как для будущей переносимой встроенной системы**.

## 4. Десять правил кода

Ниже — рабочий набор правил для этого проекта. Он вдохновлён NASA Software Engineering Handbook и подходом JPL / Power of Ten.

### 1. Пиши код с максимально простым управлением потоком.
Избегай goto, setjmp/longjmp, рекурсии и запутанных переходов. Чем проще ветвления и вызовы, тем легче тестировать, читать и проверять код.
### 2. У каждого цикла должна быть понятная верхняя граница.
Нельзя писать циклы, для которых непонятно, когда они закончатся. В safety-critical стиле важно, чтобы можно было заранее оценить время работы.
### 3. Не выделяй память динамически в рабочем цикле программы.
JPL прямо запрещает динамическое выделение памяти после инициализации. Для вашего проекта это значит: не делать new/delete в основном цикле, не плодить динамические контейнеры без необходимости, заранее создавать основные объекты.
### 4. Функции должны быть маленькими.
В оригинальном Power of 10 есть ориентир: функция примерно не длиннее одной страницы, порядка 60 строк. Смысл правила простой: одна функция — одна понятная задача.
### 5. Проверяй невозможные ситуации через явные проверки и утверждения.
В JPL-подходе рекомендуется высокая “плотность” assertions. Для студенческого проекта это можно смягчить так: в каждой важной функции должны быть проверки предусловий, диапазонов значений и инвариантов состояния.
### 6. Объявляй данные в минимально возможной области видимости.
Не держи переменные глобальными или “живущими” дольше, чем нужно. Чем меньше scope, тем меньше шанс, что значение испортят из другого места.
### 7. Проверяй все ошибки.
Возвращаемые значения нельзя молча игнорировать. Вызывающая функция должна проверять результат, а вызываемая — валидность входных параметров. Для вашего проекта это особенно важно у init(), read(), open(), log() и переходов автомата состояний.
### 8. Осторожно пользуйся препроцессором.
Макросы должны быть простыми и редкими. Не надо строить через #define сложную “магическую” архитектуру. Чем меньше условной компиляции и хитрых макросов, тем прозрачнее код.
### 9. Ограничивай сложность работы с указателями.
JPL советует жёстко ограничивать разыменование и вообще не любить чрезмерно сложные указательные конструкции. В вашем C++-проекте это переводится так: не делать хитрые цепочки указателей, не прятать владение памятью, предпочитать простые объекты, ссылки и понятную композицию классов.
### 10. Компилируй с максимальными предупреждениями и регулярно прогоняй статический анализ.
В Power of 10 и в NASA guidance очень сильный акцент на zero warnings и статической проверке кода. То есть предупреждение — это не “потом посмотрим”, а дефект, который надо устранить или переписать код так, чтобы предупреждение исчезло.

## 5. Основные классы

### `Sensor`
Абстрактный базовый класс для всех датчиков.

### `IMUSensor`
Даёт ускорение и угловую скорость.

### `BarometerSensor`
Даёт оценку высоты.

### `TemperatureSensor`
Даёт температуру.

### `BatterySensor`
Даёт напряжение питания.

### `SensorData`
Контейнер для результата чтения датчика.

### `Logger`
Пишет данные и сообщения в лог-файл.

### `FlightStateMachine`
Определяет фазу полёта по текущим данным.

### `FlightComputer`
Координирует работу датчиков, логгера и автомата состояний.

### `ScenarioGenerator`
Генерирует тестовый сценарий полёта вместо реального железа.
